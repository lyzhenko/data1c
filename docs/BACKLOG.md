### Что осталось из отзыва и где именно править (передача следующей сессии)

- **T-8. Обрезка должна быть продолжаемой.** Механизм один на все инструменты:
  `ToolSpec.MaxChars = 24_000` (`src\Data1c.Mcp\ToolSpec.cs`) и `Render.JsonOf(value, truncationHint)`
  там же; ответ при обрезке — обёртка `{truncated, limit, message, head}`. Нужно добавить в неё
  `nextOffset` (и/или курсор), чтобы ответ можно было добрать, и научить `metadata` (у него есть
  `offset` — T-3) отдавать `nextOffset = offset + maxChildren`. `grep` уже получил бюджет и `scan`
  (T-13), ему продолжение не нужно. Тесты: обрезка крупного объекта даёт `nextOffset`, а следующий
  вызов с этим `offset` отдаёт следующую порцию и в итоге `truncated: false`.
  **Решение, найденное при разведке (важно, не повторять ошибку):** наивная формула
  `nextOffset = offset + maxChildren` **теряет данные** — обрезка идёт по знакам, а не по числу детей,
  поэтому у `Document.АТЗаявкаРасчет` (около 150 детей верхнего уровня при `maxChildren = 200`) первый
  ответ успевает отдать лишь часть детей, а следующий вызов с `offset = 200` пропускает всё и отдаёт
  `truncated: false` — ложный конец. Правильно: страница должна быть самодостаточной — `metadata` сам
  уменьшает `maxChildren` до значения, при котором страница помещается в лимит, и отдаёт
  `nextOffset = offset + реально показанное число детей`; если даже при `maxChildren = 1` не влезает
  (раздутый `usages`), курсор не выдумывать, а отдавать общую обрезку с подсказкой сузить `usages`/`sections`.
- **T-7. `status` должен говорить, что уже готово.** Сейчас есть `state` строкой, `running`,

**✅ Исправлено: `conventions` на реальном индексе отвечает секундами только на новый приём.**
Причина была в том, что разбор конвенций создавался заново на каждый вызов, а его кэши (рейтинг
процедур, совпадения по методам, обращения к метаданным) живут внутри объекта разбора. Заодно
убраны два узких места: карта «последний метод в имени цели → цели» строится один раз на открытый
индекс вместо просмотра всех 540 тысяч узлов на каждый метод-признак, а имена общих модулей читаются
один раз, а не на каждый метод. Читатель индекса теперь живёт вместе с индексом (раньше
`GetIndexReader()` возвращал новый экземпляр на каждый вызов, из-за чего кэши обнулялись) и
сбрасывается при пересборке.

**Тонкость при работе с подагентами.** Их файловые инструменты разрешают относительные пути от основной
рабочей копии, а не от выданного ворктри: агент Э2-2 оставил в main семь пустых файлов-заглушек.
Инструкция подагенту должна требовать абсолютных путей к его ворктри либо работы только через команды
с `cd`.
**Чего не хватало для запуска.** Проверка без информационной базы —
`1cv8 DESIGNER /CheckModules -ConfigDir <выгрузка> /Out <журнал>` — **не работает в пакетном режиме**:
процесс висит без нагрузки и без журнала (2,5 с CPU за 11 минут, журнал 0 байт), потому что без базы
платформа уходит в диалог, а ключи `/DisableStartupDialogs` этого не меняют. Рабочий путь — через
файловую базу, как описано выше.

**Тонкость git при параллельной работе.** Ветки этапов сливались в main через `git merge --no-ff`,
история содержит merge-коммиты. `git pull --rebase` на такой ветке **переигрывает отдельные коммиты
веток и теряет слияния** — на этом я получил конфликт в середине rebase (ветка при этом не сдвинулась,
и push отправил проверенное состояние). Для синхронизации с origin на ветке со слияниями нужен обычный
`git pull` (merge) либо `git fetch` и сравнение; rebase применим только к линейной истории.

## Сценарий, под который всё делается

1. Задача ставится агенту (harness), код пишется на BSL.
2. Выгрузка конфигурации в файлы — пока вручную, дальше автоматизируется.
3. Разбор выгрузки сохраняется в **SQLite** — это данные, на которых работает агент.
4. Агент по задаче ищет существующие решения, проверяет API и метаданные, пишет код и **сам его проверяет** до вставки в Конфигуратор.
5. Цикл повторяется: правки → новая выгрузка → инкрементальная переиндексация.

Отсюда приоритет: скорость индекса, качество поиска, проверка написанного кода и корректность API платформы.
Аудит (мёртвый код, права, RLS, расширения) — вторичен.

Обозначения: **Э** — этап, **P0/P1/P2** — приоритет. Оценки в рабочих днях одного исполнителя.
«Готово когда» — проверяемый критерий.

## Тонкость окружения (P0, сделать первым)

Под полным доступом всё собирается штатно: `dotnet build Data1C.sln` → 0 ошибок, `0` предупреждений,
173 теста из 173. Но в **ограниченных режимах песочницы** (`workspace-write`, `read-only`) обычная
сборка падает **молча**: `exit 1` при «Ошибок: 0». Причина — MSBuild переиспользует дочерние узлы
через именованные каналы, а в ограниченном режиме они недоступны. Лечится так:

```powershell
dotnet build-server shutdown
dotnet build Data1C.sln -nodeReuse:false -m:1
```

Проверено: с этими флагами сборка и тесты проходят и в ограниченном режиме. Поскольку режим сессии
переключается, цикл агента не должен от этого зависеть.

**Второй, независимый случай того же симптома** (проверено 01.10.2026, выгрузка 1,2 ГБ): при
`workspace-write` песочница запускает процессы под токеном с ограничением записи (низкая метка
целостности), поэтому запись в **уже существующие** каталоги `obj`/`bin`, созданные вне песочницы,
запрещена — MSBuild падает на `MSB3491`/`MSB3021`, а сводка показывает «Ошибок: 0» и `exit 1`. Новые
каталоги внутри рабочей папки при этом доступны, то есть пересоздание `obj`/`bin` (или полный доступ)
этот случай закрывает, а `-nodeReuse:false -m:1` — нет. Диагностика: запись пробного файла в
существующий и в новый каталог внутри рабочей папки.

**Опоры для Э1-4а и Э1-5 (найдено при слиянии 01.10.2026).**

`CodeSearchService.Search(query, CodeSearchOptions, ct)` возвращает `CodeSearchResult` с попаданиями
`(Path, Line, Text, Context)`; в опциях уже есть `MaxResults`, `MaxMatchesPerFile`, `ContextLines`,
`Deadline` (по умолчанию 8 с), `Regex`, `CaseSensitive`, `Extensions`. Чего не хватает для полной замены
серверного сканирования:

1. **Фильтра по префиксам путей** — `grep` умеет `paths: ["Reports/"]`; без этого придётся сканировать всю
   выгрузку и отбрасывать попадания, а это как раз те минуты, от которых уходим.
2. **Просмотра перекрытых версий файлов** в составной выгрузке (`CompositeDumpSource.EnumerateAll`):
   иначе при базе с расширением из выдачи пропадёт версия из базы.
3. **Явного признака усечения**: сейчас ограничение задано дедлайном, и молчаливое усечение агент примет
   за полный ответ.

Обвязка владельцев уже написана (`ToolCatalog.OwnerIndex`) и переносится как есть: карта «путь модуля →
`OwnerId`» из `AnalysisResult.Modules` плюс префиксы каталогов верхнеуровневых объектов из
`AnalysisResult.Metadata.Objects` (`IsTopLevel`, `Directory`). Для `Data1c.Mcp` в Э1-5 понадобится
`ProjectReference` на `Data1c.Store` и ветка «есть индекс → отвечаем из него, нет → живой разбор».

## Порядок запуска

1. **Э0-1 → Э0-2** — скрипты сборки и кодировка: без первого агент не может проверить свои изменения, второй закрывает тихую потерю данных.

3. **Э2-2** — проверка черновика модуля: самый полезный инструмент для агента, который пишет код.
4. **Э2-1** — разбор запросов: самый крупный прирост полноты данных.
5. Дальше по потребности: **Э2-5/Э2-6** (поиск существующего и конвенции), затем **Э3** (формы и события).
