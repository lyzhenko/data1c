# Внешний отзыв: работа с выгрузкой ERP 2.5.15.49 (23 658 модулей)

Отзыв получен от потребителя, который разбирал легаси большой конфигурации (выгрузка ~9 ГБ) **через
агента**, а не через IDE. Ниже каждый пункт отзыва с результатом проверки по нашему коду и по
реальному индексу (выгрузка УНФ, 2,9 ГБ, 65 048 файлов, схема v9). Проверка важна: часть выводов
отзыва оказалась следствием устаревшей сборки сервера, а не дефектов, и наоборот — один пункт
подтвердился в более точной форме, чем был заявлен.

## Проверка по пунктам

| Пункт отзыва | Вердикт | Доказательство |
|---|---|---|
| `entrypoints` — unknown tool | **Не дефект продукта.** Инструмент зарегистрирован | `ToolCatalog.cs:60` (`EntryPointsTool()`), описание инструмента — `ToolCatalog.cs:1132`. Причина — на стороне клиента: устаревшая сборка `Data1c.Mcp.dll` или закешированный `tools/list`. В README уже описан случай: пока harness держит сервер, `Release`-сборка не перезаписывается |
| `metadata` «только id», сузить нечем | **Частично неверно, но проблема реальна в другом** | Аргументы есть: `id`, `depth` (1–4), `maxChildren` (1–500), `usages`, `usageContext` (`ToolCatalog.cs:675-687`). Дефекты настоящие: нет `sections`, нет `summary`, нет `offset`, **нет флага `truncated`** у `metadata` (он есть у `node`/`neighbors`/`entrypoints` — строки 560, 1184, 2420), а подсказка при обрезке общая («сузьте запрос (limit, depth, диапазон строк)») и для `metadata` вводит в заблуждение: диапазона строк у него нет |
| Нет поиска по содержимому модулей | **Частично неверно, реальный пробел — атрибуция** | `grep` ищет по содержимому файлов и работает на 2,9 ГБ за ~0,4 с (`ToolCatalog.cs:2335+`, `CodeSearchService`), владелец файла в ответе есть. Чего нет: **в какой процедуре найдена строка** — в `GrepHit` только `Owner` (модуль/объект), без процедуры и без `endLine`. FTS по телам модулей тоже нет (сейчас это скан файлов) |
| `UsesMetadata` возвращает пусто | **Не воспроизводится на нашей сборке.** Первый замер был неверным, второй это показал | Обращения через виртуальные таблицы **есть**: у всех 25 объектов, вызываемых как `РегистрыСведений.X.СрезПоследних` / `.Остатки` / `.Обороты`, есть входящие `UsesMetadata` к базовому объекту — от 3 до 967 (`РегистрыСведений.КурсыВалют.СрезПоследних` → `InformationRegister.КурсыВалют`: 967). Почему первый замер соврал: текст обращения по построению содержит только первые два сегмента (`РегистрыСведений.X`), поэтому `detail LIKE '%СрезПоследних%'` их не находит — «2 ребра» были артефактом фильтра, а не фактом. Обычные обращения тоже на месте: 114 792 ребра, к справочникам 21 134, к регистрам сведений 18 408 (1 091 регистр), фрагментов с `ИЗ` — 21 758, с `СОЕДИНЕНИЕ` — 10 003. Наиболее вероятная причина наблюдения — устаревшая сборка у потребителя (она же объясняет `unknown tool`); синтаксис ERP мы не проверяли, и это остаётся непокрытым |
| Нет пагинации `search` | **Верно** | Схема: `query`, `limit`, `kinds`, `includeNested`, `metadataKinds` (`ToolCatalog.cs:147-159`). `offset`/курсора нет, `total` при этом отдаётся |
| `reload` полный, инкремента нет | **Верно для MCP, но движок инкремент умеет** | `reload` без аргументов вызывает `Session.Reload()` (`ToolCatalog.cs:2314-2323`). При этом в движке есть частичная переиндексация модулей (`IndexWriter.WriteModuleFiles`, замер 0,34 с), наблюдение за файлами и тест `PartialWatchTests`. В MCP это не выведено, а `status` показывает `watching: false` |
| Прогресс не говорит, что уже готово | **Верно** | Есть `state` строкой, `running`, `indexReady`, `rebuilding`; нет разбивки `ready: {metadata, search, graph}` |
| Обрезка должна быть продолжаемой | **Верно** | `truncated: true` и подсказка есть, курсора/`nextOffset` нет — добрать нельзя |
| Добавить `endLine` и модуль вызывающего | **Верно, дешёвая правка** | В `neighbors` есть `line`, `detail`, теги (`routineKind`, `export`, `lines`, `startLine`, `region`, `directives`); `endLine` и модуль вызывающего отсутствуют |

## Что отзыв просил не ломать (защищать тестами)

1. `incoming`/`outgoing` в результатах `search` — главный сигнал триажа (узел или листик).
2. Номера строк в рёбрах вместе с `detail` — без них связь «кто вызывает» бесполезна.
3. `found` против `total` — честно показывает, что список урезан.
4. Различение одноимённых объектов (`InformationRegister.X` и `Document.X`) по `metadataKind`.
5. `code` с окружением и нумерацией (строки и границы процедуры) — читается как diff-контекст.
6. `platform` с версией платформы и доступностью справки.
7. Машинно-цепляемые идентификаторы `routine:module:…#Имя`, `call:…`.

## Задачи из отзыва

Приоритеты: сначала то, что блокирует целые классы задач у агента, потом качество ответов,
потом эргономика.

### P0 — блокирует классы задач

- **T-1. Атрибуция найденной строки к процедуре.** `grep` (и, по возможности, `search` по содержимому)
  должен возвращать `routine { id, name, startLine, endLine }` и `module`. Данные есть в индексе:
  `symbols` хранит границы процедур по модулю, нужен поиск процедуры по строке (двоичный поиск по
  диапазонам). Без этого агент считает принадлежность вручную — на легаси это основной сценарий.
  *Проверка:* тест на модуль с директивами `#Если` и вложенными процедурами; замер на выгрузке.
- **T-2 — проверено, дефекта нет.** Виртуальные таблицы (`.СрезПоследних`, `.СрезПервых`, `.Остатки`,
  `.Обороты`) уже дают `UsesMetadata` на базовый объект — и в текстах запросов, и в вызовах менеджера
  из кода. Доказательство на нашей выгрузке: 25 объектов, вызываемых через виртуальные таблицы,
  у всех есть входящие обращения к базовому объекту (3…967). Зачем всё же остаётся пункт: синтаксис
  ERP не проверялся, и если у потребителя повторится пустой `neighbors`, первым делом надо смотреть
  `status.server.builtAt` — свежая ли сборка отвечает. Регрессия закреплена тестом
  `ВиртуальнаяТаблицаЭтоОбращениеКБазовомуОбъекту` (вызов из кода) и существующими тестами
  `QueryParserTests` (виртуальная таблица в тексте запроса).
- **T-3. `metadata`: управляемая выдача и честная обрезка.** Аргументы `sections`
  (`Attribute`, `TabularSection`, `Form`, `Command`, `Template`, `Module`), `summary: true`
  (только счётчики по разделам), `offset`; **флаг `truncated` в ответе**; подсказка при обрезке —
  с перечислением именно тех аргументов, которые у инструмента есть.
- **T-4. Диагностика устаревшей сборки в `status`.** Отдавать сборку/время файла `Data1c.Mcp.dll`,
  версию схемы и число инструментов. Два ложных вывода отзыва (`unknown tool`, «у metadata только id»)
  объясняются старой сборкой — это должно быть видно с первого вызова, а не выясняться перепиской.

### P1 — качество ответов

- **T-5. Пагинация `search`:** `offset` (или курсор) вместе с уже отдаваемым `total`.
- **T-6. Инкрементальный `reload`:** `reload(paths: [...])` плюс отчёт «что изменилось с прошлого раза»;
  движок уже умеет (`WriteModuleFiles` — 0,34 с, наблюдение за файлами), нужно вывести в MCP и
  включать наблюдение по умолчанию там, где это уместно.
- **T-7. `status`: готовность по частям** — `ready: { metadata, search, graph }`, чтобы агент знал,
  какие запросы уже осмысленны, а какие дадут неполный граф.
- **T-8. Продолжаемая обрезка:** `truncated: true` плюс `nextOffset`/курсор, чтобы ответ можно было
  добрать порциями. Для агента с конечным контекстом это принципиально.

### P2 — эргономика

- **T-9. `endLine` и имя вызывающего модуля** в `neighbors` (и в `node` для рёбер) — цепочки вызовов
  строятся без дополнительных запросов.
- **T-10. FTS по телам модулей** — мгновенный поиск по содержимому вместо скана файлов (сейчас
  `grep` ~0,4 с на 2,9 ГБ; это приемлемо, но с индексом будет быстрее и позволит ранжирование).
- **T-11. Записать в память проекта** особенность окружения (кириллица в inline-командах оболочки)
  и правило «скрипты через файл или через MCP».

## Оговорки о выборке

Отзыв получен на одной конфигурации (ERP 2.5.15.49, 23 658 модулей) и одном сценарии — разбор легаси
агентом. Проверка выполнена на нашей выгрузке (УНФ) и на нашем коде; числа по ERP не воспроизводились.
Пункт про `entrypoints` и частично про `metadata` объясняются устаревшей сборкой у потребителя —
это гипотеза, подтверждённая кодом (инструмент зарегистрирован, аргументы объявлены), но не логи
клиента, которых у нас нет.
