# Data1C

Исследовательский проект: разбор выгрузки конфигурации 1С (формат «Выгрузить конфигурацию в файлы» —
XML + BSL) и построение **графа зависимостей**: объекты метаданных, модули, процедуры и связи между ними.

Целевая платформа — .NET 10, C#.

## Состав решения

| Проект | Назначение |
|---|---|
| `src/Data1c.Core` | **Библиотека — основная разработка.** Абстракции ввода, модель метаданных, лексер и структурный разбор BSL, модель платформы из справки `.hbk`, сборка графа, запросы к графу, экспорт в JSON и Graphviz DOT |
| `src/Data1c.FileSystem` | **Слой работы с 1С.** Реализации абстракций библиотеки поверх файловой системы: каталог выгрузки конфигурации и справочные файлы `.hbk` установленных платформ |
| `src/Data1c.Store` | **Слой базы данных.** SQLite-индекс выгрузки: схема, запись разбора, чтение (поиск узлов и символов, карточка узла, соседи, обращения к метаданным, обход связей) |
| `src/Data1c.Mcp` | **Сам сервер.** MCP-сервер (stdio) для ИИ-агентов: навигация по выгрузке, чтение кода, справка платформы, проверка модулей |
| `tests/Data1c.Tests` | Тесты (xunit 2.9.3) |
| `tools/Data1c.TestRunner` | Раннер тестов: в этом окружении `dotnet test` не запускается (см. «Тесты») |
| `tools/harness` | Фрагмент подключения MCP-сервера к harness |
| `docs/` | План работ и иллюстрации |

> Консольное приложение `data1c` и просмотрщик графа вынесены в ветку **`cli`** (`git switch cli`).
> На `main` их нет: интерфейс для агента — MCP-сервер, а консольные команды, страница просмотрщика и
> её документация живут в ветке `cli` — она собрана от актуальной библиотеки.

Разделение ответственности: библиотека не знает, откуда берутся файлы — она работает через
`IDumpSource` и `IPlatformSource`. Файловый доступ реализует `Data1c.FileSystem`, хранение индекса —
`Data1c.Store`, протокол для агента — `Data1c.Mcp`. Благодаря этому библиотеку можно направить
на zip-архив, базу данных или тестовый набор в памяти.

## Быстрый старт

```powershell
dotnet build Data1C.sln

# тесты (штатный dotnet test в этом окружении не работает)
dotnet run --project tools\Data1c.TestRunner

# MCP-сервер: выгрузку можно задать аргументом или открыть инструментом open
dotnet src\Data1c.Mcp\bin\Debug\net10.0\Data1c.Mcp.dll --dump C:\dump\1c_files --platform
```

## MCP-сервер: разработка на 1С из ИИ-агента

`src/Data1c.Mcp` — MCP-сервер (stdio, JSON-RPC 2.0) над библиотекой. Он даёт агенту то, что нужно при
разработке на BSL: найти объект или процедуру, посмотреть состав объекта метаданных, прочитать код,
узнать, кто вызывает процедуру, свериться со справкой платформы и проверить модуль после правки.
Внешних зависимостей у сервера нет — только BCL, поэтому он собирается без доступа к nuget.org.

```powershell
# без выгрузки: путь открывается инструментом open
dotnet src\Data1c.Mcp\bin\Release\net10.0\Data1c.Mcp.dll --platform

# с фиксированной выгрузкой
dotnet src\Data1c.Mcp\bin\Release\net10.0\Data1c.Mcp.dll --dump C:\dump\1c_files --platform

dotnet src\Data1c.Mcp\bin\Release\net10.0\Data1c.Mcp.dll --help
```

stdout занят протоколом, вся диагностика идёт в stderr.

| Инструмент | Зачем |
|---|---|
| `status` | идёт ли разбор, статистика графа, предупреждения и ошибки |
| `open` | открыть (или сменить) выгрузку: `paths` — база и расширения, расширение перекрывает базу по совпадающим путям |
| `search` | найти по имени, синониму, идентификатору или пути файла: объекты, модули, процедуры, а также реквизиты и табличные части (`includeNested`) |
| `grep` | поиск по **тексту** файлов: подстрока или regex, фильтры по расширениям и путям, контекст, лимит; в ответе — источник, строка и объект-владелец |
| `node` | карточка узла и его связи со строками кода; у объекта метаданных — краткая сводка обращений `usages`, аргумент `usageContext` оставляет один контекст |
| `neighbors` | окружение узла: кто вызывает (`edgeKinds: ["Calls"]`, `direction: "in"`) и что вызывает он |
| `code` | исходный текст модуля, процедуры или XML с номерами строк |
| `metadata` | состав объекта деревом: реквизиты, табличные части и **их** реквизиты, формы, команды, типы, модули; раздел `usages` показывает, кто и в каком контексте читает объект, аргумент `usageContext` оставляет один контекст (счётчики, читатели и примеры пересчитываются); у формы — реквизиты, элементы с привязкой `DataPath`, команды и обработчики событий с процедурами модуля формы |
| `platform` | справка установленной платформы: синтаксис и описание методов и типов |
| `check` | проверка модуля или **черновика** (`text`): структура (процедуры, области, вызовы) и замечания по смыслу с позициями — неизвестная процедура (всегда ошибка: глобальные функции платформы узнаются по встроенному списку из 989 имён, а не по подключённой справке), число аргументов (в том числе у методов платформы по справке), отсутствующий объект метаданных с подсказкой похожих, неиспользуемые переменные и параметры, функция без `Возврат` |
| `types` | таблица символов модуля и консервативный вывод типов: объявления с позициями и областью видимости, выведенные типы, вызовы, разрешённые как методы платформы, и места, где тип вывести не удалось; `line` добавляет видимые в строке имена с типами |
| `similar` | поиск готовой реализации: признаки черновика (вызовы методов платформы, обращения к метаданным из кода и запросов, вызовы процедур, термы имени и комментария) взвешены обратной частотой, поэтому частые методы вроде `Структура.Вставить` реализации не различают, а редкие — различают; вызовы процедур сравниваются **по идентификатору разрешённой цели**, так что квалификация вызова не влияет, а неразрешённые вызовы дают слабое совпадение по имени метода; в ответе оценка, совпавшие сигналы и объяснение |
| `conventions` | «в конфигурации это уже делают так»: по намерению (`intent`) или методу платформы (`platform`) — рейтинг процедур и общих модулей по числу вызовов с примерами и объяснением, почему подходит; каталог **двадцати** типовых приёмов, ответ объясняет распознавание (ступень, слова, метод, вес) |
| `entrypoints` | точки входа: подписки на события, регламентные задания, обработчики событий форм; `metadata` отвечает «кто реагирует на изменения этого объекта», `kind` сужает вид; у каждой точки входа — обработчик и идентификатор процедуры |
| `rights` | права и RLS из `Roles/*/Ext/Rights.xml`: `metadata` — какие роли и какие права имеют на объект, `role` — что может роль; **текст условия ограничения доступа хранится в индексе** (`metadata_refs.condition`), аргумент `conditionContains` ищет по нему («у каких ролей условие упоминает Организацию»); назначение ролей пользователям в выгрузку не входит |
| `reload` | перечитать выгрузку, когда модули уже изменены на диске |

Рабочий цикл агента: `open` → `status` → `search`/`grep`/`metadata` (в карточке объекта — `usages`: кто
и в каком контексте его читает) → `similar`/`conventions` (что уже сделано похожего и как принято
в конфигурации) → `code`/`types`/`entrypoints`/`rights` → правка файлов выгрузки штатными средствами
агента → `check` (в том числе по тексту черновика) → `reload`.

**Несколько источников.** `open` принимает список путей: первый — база конфигурации, следующие —
расширения. По совпадающим относительным путям (в расширении 1С adopted-модуль лежит там же, где в
базе) эффективным считается файл из последнего источника — так его видят граф и `code`; корневые файлы
(`Configuration.xml`, `ConfigDumpInfo.xml`) всегда берутся из базы, иначе расширение подменило бы корень
конфигурации. При этом `grep` ищет **во всех** источниках и у каждого совпадения указывает `source` и
признак `overridden`, поэтому версия из базы не теряется. Ключ `--dump` можно повторять.

### Подключение к harness

Строка подключается штатным MCP-клиентом harness (`@deepseek-ai/dsh-mcp-client`), инструменты
появляются у модели как `mcp__data1c__<имя>`. Готовый фрагмент лежит в
`tools/harness/mcp-data1c.patch.yml`: его вставляют в патч профиля
(`%USERPROFILE%\.dsh\profiles\desktop\cordis.patch.yml` или `...\web\cordis.patch.yml`) и
перезапускают harness.

```yaml
- insert:
    - id: mcp-data1c
      name: "@deepseek-ai/dsh-mcp-client"
      config:
        serverName: data1c
        transport: stdio
        command: 'C:\Program Files\dotnet\dotnet.exe'
        args:
          - 'D:\dev\data1c\src\Data1c.Mcp\bin\Release\net10.0\Data1c.Mcp.dll'
          - '--platform'
        toolCallTimeoutMs: 1800000
```

Путь к выгрузке намеренно не зафиксирован: агент открывает нужную выгрузку через `open`, поэтому одна
строка работает для любого проекта. Любой другой MCP-клиент подключается так же — командой и
аргументами, без правок кода.

### Что стоит помнить

- Разбор идёт один раз на процесс и переиспользуется. На конфигурации ~1,2 ГБ BSL (23 600 модулей,
  117 000 файлов) в сборке `Debug` он занимает единицы минут, поэтому первый вызов `search`,
  `metadata`, `node` или `check` отвечает долго — держите таймаут вызова с запасом
  (`toolCallTimeoutMs` в примере выше рассчитан на это).
- `grep` разбор **не ждёт**: он ищет по файлам сразу, а разбор использует только для имён владельцев,
  ожидая его не дольше `waitMs` (по умолчанию 60 с). Если разбор не успел, ответ содержит
  `ownersResolved: false` и подсказку — повторите поиск позже, владельцы появятся.
- Разбор — снимок. После правки модулей вызывайте `reload`, иначе поиск и граф покажут прежнее
  состояние; `code` и `check` читают файлы с диска и видят правку сразу.
- Ограничения разрешения вызовов те же, что у графа: вызовы через переменные остаются внешними узлами
  `call:<текст>`, поэтому «кто вызывает» точно отвечает для процедур и общих модулей.
- Ответы инструментов ограничены по размеру: сужайте запрос через `limit`, `depth`, `from`/`to`.
  `grep` останавливается, набрав `limit`, поэтому `filesScanned` в ответе — это «сколько успел
  просмотреть до останова», а не размер выгрузки.
- Пока harness держит сервер запущенным, сборка `Release` не может перезаписать
  `bin\Release\net10.0\Data1c.Mcp.dll` (файл занят процессом сервера). Перезапустите harness или
  соберите `Debug` — плагин можно направить на сборку `Debug` тем же ключом `args`.

## SQLite-индекс выгрузки

**MCP-сервер отвечает из индекса по умолчанию.** Если файла `<выгрузка>/.data1c/index.db` нет,
сервер соберёт его при первом запросе инструмента и дальше будет только читать; путь можно задать
ключом `--index <файл>`, а прежний режим с разбором в память включается ключом `--no-index`.

Замеры на выгрузке УНФ (2,9 ГБ): с готовым индексом `initialize` 24 мс, `tools/list` 12 мс,
`status` 163 мс, `search` 63 мс, `node` 16 мс, `neighbors` 14 мс, `metadata` 1 мс, `check` 52 мс,
`grep` 404 мс, `platform` 1–2 мс — разбора в память при старте не происходит вовсе, справка платформы
прогревается в фоне. Без индекса первый запрос собирает его (32 с на секции общих модулей, 993 МБ),
повторный — 1 мс.

Ключ `--watch <секунды>` включает наблюдение за выгрузкой: сервер сравнивает состояние файлов с
индексом и при изменениях пересобирает индекс в фоне, продолжая отвечать из прежнего. Так новая
выгрузка подхватывается без ручного шага; `status` показывает `dumpChange` и `fresh`.

**Правка модуля переиндексируется частично и мгновенно.** Идентификаторы процедур не зависят от
содержимого (`routine:module:<путь>#Имя`), поэтому при изменении модуля обновляются только его узлы,
связи и символы, а вызовы из других модулей остаются на месте. Метаданные из XML при этом не
перечитываются: владелец и вид модуля берутся из индекса. На выгрузке 2,9 ГБ правка модуля занимает
**0,98 с** вместо ~98 с полной пересборки; результат сверяется с полной сборкой в тестах. Если
изменились файлы XML, что-то удалено или затронута заметная часть выгрузки, сервер честно пересобирает
индекс целиком.

Размер индекса и скорость сборки настраиваются: `--no-external` не держит внешние цели (1791 МБ
вместо 2973 МБ, сборка 38 с вместо 55), а новые базы создаются со страницей 8 КБ. Замеры на любой
выгрузке печатает `tools/Data1c.Benchmark`.

Разбор можно сохранить в базу и дальше отвечать на вопросы по ней — без повторного разбора гигабайтов
модулей на каждый запуск. Это основной режим для работы агента: индекс открывается за десятки
миллисекунд. Индекс собирает `Data1c.Store` (`IndexWriter`, `SqliteIndex`); командная строка
`data1c index` живёт в ветке **`cli`**.

```csharp
using var index = SqliteIndex.Open(@"C:\index\unf.db");        // OpenReadOnly — для готового файла
var source = new FileSystemDumpSource(@"C:\dump\1c_files");
var result = new DumpAnalyzer().Analyze(source);
new IndexWriter(index).Write(source, result);                  // схема версионируется самим индексом
```

Что лежит в индексе: `nodes` и `edges` (граф зависимостей), `symbols` (процедуры, функции, области,
комментарии и параметры), `metadata_objects` и `metadata_items` (объекты, реквизиты и их типы),
`metadata_refs` (обращения из кода, типы, права), `files` (размер и время правки — основа будущей
инкрементальной переиндексации), а также FTS5-таблицы `nodes_fts` (префиксный поиск по именам,
unicode61) и `terms_fts` (термы для смыслового ранжирования).

Замеры на выгрузке УНФ (2,9 ГБ, 14 737 модулей, схема v7):

| Показатель | Значение |
|---|---|
| Записано | 546 922 узла, 2 634 495 связей, 297 130 символов, 84 165 объектов метаданных, 114 804 обращения (из них 31 296 из текстов запросов), 6 026 форм |
| Файл индекса | 3262 МБ |
| Разбор выгрузки | 32,5 с (таблица символов, вывод типов, запросы, формы, число параметров) |
| Запись индекса | 73,0 с |
| Правка одного модуля | 0,34 с |
| Открытие только для чтения | 44 мс |
| Поиск узла по префиксу | 3–4 мс |
| Поиск по подстроке | 6 мс (заведомо без совпадений — 217 мс) |
| Поиск символов по подстроке | 8 мс |
| Объекты метаданных по имени и синониму | 0 мс |
| Кто вызывает по имени вызова | 20–30 мс |
| Кто использует объект метаданных | 3 мс |
| Карточка узла со связями | 1 мс |
| Обход связей на 2 шага | 24–197 мс (зависит от узла) |

Схема версионируется: если файл индекса собран другой версией, запись пересобирает его заново,
а `SqliteIndex.OpenReadOnly` сообщает о несовместимости. Обходы связей выполняются
рекурсивными SQL-запросами без временных таблиц, поэтому работают и на индексе, открытом только
на чтение.

## Публичный API библиотеки

| Тип | Роль |
|---|---|
| `IDumpSource`, `DumpFile`, `InMemoryDumpSource` | источник файлов выгрузки; реализация для каталога — в `Data1c.FileSystem` |
| `MetadataDumpReader`, `MetadataReadOptions`, `MetadataReadResult` | чтение XML-метаданных: `MdObjectModel`, файлы модулей, предупреждения |
| `MdObject`, `MdKind`, `MdReference`, `MdNaming`, `MdRefParser` | модель метаданных и разбор строковых ссылок (`cfg:CatalogRef.Товары`) |
| `BslLexer`, `BslModuleParser` (`IBslModuleParser`), `BslModuleInfo` | лексика и структура BSL: процедуры, функции, области, директивы, вызовы, обращения к метаданным |
| `DependencyGraphBuilder`, `DependencyGraph`, `GraphNode`, `GraphEdge` | сборка и представление графа |
| `IPlatformSource`, `PlatformInstallation`, `PlatformHelpFile`, `InMemoryPlatformSource` | источник справочных файлов платформы; реализация для каталога 1С — в `Data1c.FileSystem` |
| `HbkArchive`, `HbkTopicReader` | чтение контейнера `.hbk` и превращение HTML-тем в текст |
| `PlatformHelpIndex`, `PlatformHelpOptions`, `PlatformTopic` | модель платформы: выбор версии, поиск темы, распознавание метода платформы |
| `GraphQueryService` | запросы к графу: поиск узлов, окружение узла, карточка узла |
| `SourceCodeReader`, `CodeFragment` | чтение исходных текстов модулей и XML по требованию (для панели кода) |
| `GraphJsonWriter`, `GraphDotWriter` | экспорт графа |
| `DumpAnalyzer`, `AnalysisOptions`, `AnalysisResult` | сквозной сценарий: выгрузка → метаданные → BSL → граф |

Пример:

```csharp
var source = new FileSystemDumpSource(@"C:\dump\1c_files");   // реализация из Data1c.FileSystem
var result = new DumpAnalyzer().Analyze(source);

Console.WriteLine(result.Graph.Statistics.NodeCount);

var routine = "routine:module:CommonModules/ОбщегоНазначения/Ext/Module.bsl#МояПроцедура";
foreach (var caller in result.Graph.Callers(routine))
{
    Console.WriteLine(caller);
}
```

## Экспорт графа

Граф отдаёт библиотека: `GraphJsonWriter` пишет JSON, `GraphDotWriter` — DOT для Graphviz (`dot -Tsvg`),
`GraphQueryService` отвечает на запросы к графу — поиск узлов, окружение, карточка узла.

Интерактивный просмотрщик графа и консольные команды (`data1c view`, `scan`, `index`, `search`,
`platform`, `stats`) входят в консольное приложение `data1c` — оно вместе со своей документацией
живёт в ветке **`cli`**.

## Формат выгрузки 1С: что выяснено на реальной конфигурации

Выгрузка — это каталог с XML и BSL (не `.cf`/`.dt`). Формат `version="2.20"`, пространство имён
`http://v8.1c.ru/8.3/MDClasses`. Наблюдённые размеры: ~65 000 файлов, ~2.9 ГБ, из них ~628 МБ BSL и
~43 000 XML; файлы `*.bin` (макеты, драйверы оборудования) — основной объём и в разборе не участвуют.

Раскладка объектов:

```
Configuration.xml                       корень конфигурации + список детей по именам
ConfigDumpInfo.xml                      служебный (версии объектов)
Ext/*.bsl                               модули конфигурации (ManagedApplicationModule, SessionModule, ...)
<Секция>/<Имя>.xml                      объект метаданных
<Секция>/<Имя>/Ext/ObjectModule.bsl     модуль объекта
<Секция>/<Имя>/Ext/ManagerModule.bsl    модуль менеджера
<Секция>/<Имя>/Forms/<Форма>.xml        форма
<Секция>/<Имя>/Forms/<Форма>/Ext/Form/Module.bsl
<Секция>/<Имя>/Commands/<Команда>/Ext/CommandModule.bsl
<Секция>/<Имя>/Templates/<Макет>/Ext/Template.xml|.bin
Roles/<Имя>/Ext/Rights.xml              права роли
Subsystems/<Имя>.xml                    подсистема, состав — через <xr:Item xsi:type="xr:MDObjectRef">
```

Особенности, которые учитывает reader:

- **Вложенные объекты и ссылки по имени.** `ChildObjects` родителя содержит как полноценные объекты
  (`<Attribute>` с `<Properties>`), так и ссылки по имени (`<Form>ФормаЭлемента</Form>`). Reader
  разбирает и то и другое, а затем заменяет ссылку полноценным объектом из отдельного файла.
- **Привязка модулей по пути.** Каталог объекта — это каталог его XML-файла плюс имя файла без
  расширения (`Catalogs/Товары`, `Catalogs/Товары/Forms/ФормаЭлемента`). Модуль привязывается подъёмом
  по каталогам пути до первого совпадения, поэтому одинаково работают `Ext/ObjectModule.bsl`,
  `Forms/<Форма>/Ext/Form/Module.bsl` и модули команд, у которых нет собственного XML-файла.
- **Не разбираются** (пропускаются по имени файла, содержимое не читается): `Rights.xml` (по умолчанию),
  `Form.xml` (logform управляемой формы), `Template.xml`, `Picture.xml`, `Help.xml`, `Package.xml`,
  `CommandInterface.xml`, `ClientApplicationInterface.xml`, `MainSectionCommandInterface.xml`,
  `HomePageWorkArea.xml`, `Logo.xml`, `Splash.xml`, `MainSectionPicture.xml`, `Schedule.xml`,
  `Flowchart.xml`, `DCS.xml`. Разбираются только файлы с корнем `MetaDataObject`.
- **Незавершённая выгрузка.** 1С пишет файлы последовательно и часть из них удерживает открытыми.
  Reader открывает файлы с `FileShare.ReadWrite | FileShare.Delete`, а занятые и частично записанные
  файлы пропускает с предупреждением — разбор не падает. Если `Configuration.xml` недоступен, корень
  конфигурации создаётся синтетически, а объекты из `ChildObjects` остаются в модели как ссылки по имени.

## Модель платформы (справка .hbk)

Выгрузка конфигурации не содержит описания самой платформы, поэтому методы встроенных типов
(`Массив.Добавить`, `Запрос.Выполнить`, `СтрНайти`) для анализатора — просто текст. Пробел
закрывает справка установленной платформы: `bin\shcntx_ru.hbk` (синтакс-помощник),
`shlang_ru.hbk` (язык), `shquery_ru.hbk` (язык запросов). Файлы читаются из установленной 1С,
поэтому модель всегда совпадает с версией платформы; текст справки при этом никуда не копируется
и не распространяется.

```text
# MCP-инструмент сервера (сервер запускается с ключом --platform)
platform query="Массив.Добавить"                 # тема целиком
platform query="ТаблицаЗначений" mode=search     # поиск по справке
```

```csharp
var index = new PlatformHelpIndex(new FileSystemPlatformSource());
var topic = index.Find("Массив.Добавить");
```

**Формат контейнера.** `.hbk` не документирован. Со смещения 47 идёт таблица из семи записей по
12 байт: адрес записи с именем файла и адрес начала цепочки блоков; среди записей ищется
`FileStorage`. Содержимое собрано из цепочки блоков: заголовок блока — 31 байт ASCII, где поля
`[2..10)`, `[11..19)` и `[20..28)` — шестнадцатеричные числа: объявленный размер всей записи
(заполнен только в первом блоке), размер данных этого блока и адрес следующего блока. Склеенная
нагрузка — ZIP-архив с HTML-темами.

Ключевая тонкость: **данные блока читаются по второму полю, а не по первому**. Первое поле — размер
всей записи, и в многофайловых контейнерах он больше блока (в 8.3.27 у `shlang_ru.hbk` 68 634 против
42 549), поэтому чтение «по первому полю» собирает мусор и ZIP не открывается. Имена тем внутри
контейнера служебные (`objects.catalog234.Array.methods.Add772`), а человекочитаемое имя лежит в
заголовке темы: `Массив.Добавить (Array.Add)`. Поиск идёт и по служебному имени, и по обоим
псевдонимам заголовка — русскому и английскому.

**Как это влияет на граф.** С `--platform` неразрешённый вызов проверяется по справке: если в ней
есть тема или заголовок ровно с таким именем, узел получает тип `Platform` и теги `platformTitle`
и `platformVersion`. Правило намеренно строгое и текстовое — методы платформы названы в справке
полным именем (`Массив.Добавить (Array.Add)`, `Запрос.Выполнить`), поэтому совпадение точное.
Обратная сторона: переменная, названная как тип (`Массив = Новый Массив; Массив.Добавить(...)`),
даст тот же узел, а `Объект.Добавить` или `ДополнительныеПараметры.Вставить` платформой не
считаются. Побочный эффект: вызовы глобальных функций платформы из разных модулей перестают
плодить отдельные заглушки и собираются в один узел — на реальной конфигурации внешних узлов стало
244 408 вместо 251 707.

## Модель графа

Узлы (`GraphNodeKind`): `Configuration`, `MetadataObject`, `Module`, `Routine`, `External`, `Platform`.
Связи (`GraphEdgeKind`): `Contains` (вложенность), `References` (ссылки метаданных), `Defines`
(объявление процедуры), `Calls` (вызов), `UsesMetadata` (обращение к метаданным из кода).

Идентификаторы узлов:

| Узел | Пример |
|---|---|
| Конфигурация | `Configuration` |
| Объект метаданных | `Catalog.Товары` |
| Вложенный объект | `Catalog.Товары/Form.ФормаЭлемента` |
| Модуль | `module:CommonModules/ОбщегоНазначения/Ext/Module.bsl` |
| Процедура / функция | `routine:module:CommonModules/.../Module.bsl#МояПроцедура` |
| Цель вне выгрузки | `call:ОбщегоНазначения.ЗначениеРеквизитаОбъекта`, `Catalog.ЕдиницыИзмерения` |
| Метод платформы (с `--platform`) | `platform:Массив.Добавить`, `platform:Запрос.Выполнить` |

Разрешение вызовов: локальный вызов (`МояПроцедура()`) ищется в том же модуле; вызов
`ОбщийМодуль.Метод()` разрешается в процедуру соответствующего общего модуля; далее вызов
проверяется по модели платформы (если она подключена); всё остальное (вызовы через переменные,
методы менеджеров) фиксируется внешним узлом `call:<текст вызова>`, поэтому ни одна зависимость
не теряется.

Осознанные ограничения: реквизиты и табличные части по умолчанию не становятся узлами графа
(их ссылки приписываются ближайшему родителю, чтобы типы не пропадали) — включается опцией
`IncludeNestedObjects` / `--nested`; без модели платформы вызовы платформенных методов не
отделяются от пользовательских (`--platform` включает классификацию); вызовы через переменные
требуют вывода типов и пока остаются внешними.

## Проверка на реальной конфигурации

Замеры на выгрузке «1С:Управление нашей фирмой» (~65 000 файлов, 2.9 ГБ, из них 628 МБ BSL,
43 000 XML), 32-ядерная машина, `Release`:

| Показатель | Значение |
|---|---|
| Разбор метаданных | 27 257 XML-файлов, 0 ошибок, ~11 с |
| Разбор BSL | 14 737 модулей (628 МБ), 0 предупреждений |
| Объекты метаданных | 84 166, из них 16 256 верхнего уровня |
| Процедуры и функции | 191 608 процедур + 67 224 функции |
| Граф | 570 889 узлов, 2 603 941 связь |
| Модель платформы | 8.3.27.2214: 25 545 тем из трёх файлов, 608 узлов `Platform` |
| Полный проход (`stats`) | ~20 с, пик рабочего набора 2.8 ГБ (с `--platform` ~22 с) |
| Экспорт полного графа в JSON | ~25 с, 1.1 ГБ |

Распределение связей: `Calls` 2 131 935, `Defines` 258 832, `UsesMetadata` 83 508, `References` 69 317,
`Contains` 60 349. Внешних узлов 251 707, а с `--platform` — 244 408: это вызовы через переменные и
методы менеджеров (`call:Объект.Метод`), которые по тексту модуля разрешить нельзя. Платформенными
признаны 608 узлов, среди них самые вызываемые — `Тип` (34 375 вызовов),
`Запрос.УстановитьПараметр` (30 524), `Запрос.Выполнить` (15 588), `ТабличныйДокумент.Вывести` (3 211),
`РезультатЗапроса.Выбрать` (2 428), `Дата` (2 272). Остальные обращения к платформе идут через
переменные (`ДополнительныеПараметры.Вставить`) и требуют вывода типов.

Полный граф в JSON занимает больше гигабайта, поэтому для просмотра и обмена удобнее ограничивать
разбор: `--sections`, `--no-routines`, `--no-calls` или формат DOT с `--dot-max-nodes`.

## Тесты

```powershell
dotnet run --project tools\Data1c.TestRunner\Data1c.TestRunner.csproj                                  # все тесты
dotnet run --project tools\Data1c.TestRunner\Data1c.TestRunner.csproj -- --filter=Data1c.Tests.Metadata # подмножество
dotnet run --project tools\Data1c.TestRunner\Data1c.TestRunner.csproj -- --filter=Data1c.Tests.Platform # модель платформы
dotnet run --project tools\Data1c.TestRunner\Data1c.TestRunner.csproj -- --filter=Data1c.Tests.Mcp      # MCP-сервер
```

Всего **435 тестов** (из них около 70 — на MCP-сервер и 5 — на составную выгрузку). Контейнер `.hbk` проверяется на синтетическом файле, который тест собирает сам
(это же фиксирует понимание формата), а `RealPlatformTests` читает настоящий `shcntx_ru.hbk`
установленной платформы и печатает найденные цифры; если платформы на машине нет, тест проходит
вхолостую.

Собирать и запускать проще скриптами: `tools\build.ps1` и `tools\test.ps1` (сброс серверов сборки,
`-nodeReuse:false -m:1`, понятный итог и коды возврата; `test.ps1` понимает `-Configuration`, `-Filter`,
`-NoBuild`). Тексты выгрузки читаются общим `Data1c.Core.Dump.DumpTextReader`: BOM → строгий UTF-8 →
запасная CP1251, поэтому выгрузки в CP1251 разбираются наравне с UTF-8.

Стандартный `dotnet test` в этом окружении неприменим: testhost падает с `Win32Exception (5)` при
попытке открыть handle родительского процесса. `tools/Data1c.TestRunner` — минимальный раннер,
который находит `[Fact]`/`[Theory]` по отражению и выполняет их (код возврата 1 при падениях).

## Что дали вторая волна этапов Э2 и Э3 (проверено на выгрузке 2,9 ГБ)

- **Обращения к объекту.** В карточке объекта — раздел `usages` с разбивкой по контекстам: у
  `Catalog.Номенклатура` 1397 обращений (565 из запросов, 421 в типах, 289 в коде, 5 в правах ролей),
  у `InformationRegister.КурсыВалют` — 979 (795 из запросов). Счётчики контекстов есть и в `status`.
- **Похожий код.** `similar` на черновике с запросом к `РегистрСведений.КурсыВалют` за 197 мс вернул
  первым `CommonModules/РаботаСКурсамиВалют`; частые методы платформы вроде `Запрос.Выполнить`
  в примечаниях честно помечены как неразличающие.
- **Конвенции.** `conventions` отвечает «так уже делают» и объясняет распознавание (каталог 20 приёмов,
  ступень, слова, метод, вес). Замер на прогретом реальном индексе 3,3 ГБ: первый запрос нового приёма —
  4,1–4,9 с (работа идёт на каждый метод-признак: чтение вызывающих и сведения о них), а повторный
  и пересекающийся по методам — **159–244 мс**: разбор конвенций держится на сессию и переиспользует
  рейтинг процедур, совпадения по методам и карту «метод → целевые узлы».
  Было 4,5–6,3 с на любой запрос.
- **Точки входа.** `entrypoints` видит 454 подписки на события, 189 регламентных заданий и 52 214
  обработчиков форм; фильтр по объекту отвечает, кто реагирует на его изменения.
- **Права и RLS.** `rights` разбирает 1 030 ролей: у `Catalog.Номенклатура` права дают 5 ролей, у роли
  `ПолныеПрава` — 2 401 объект; условия RLS (1 707 объектов в 405 ролях) лежат в индексе
  (`metadata_refs.condition`, схема v9), `status` показывает их число, `conditionContains` ищет по тексту
  («Организация» — 1 453 условия у 337 ролей и 663 объектов).
- **Разбор кода внутри `#Если`.** Раньше заголовки процедур внутри директив препроцессора не разбирались:
  модулей с символами было 10 028 из 14 737, у `CommonModules/ОбщегоНазначения/Ext/Module.bsl` —
  1 символ, и 426 428 вызовов (20 %) были приписаны модулям без символов. Теперь 13 722 модуля с символами,
  у `ОбщегоНазначения` 285 процедур, а «вызовов в модулях без символов» осталось 1 (0,0 %). Одноимённые
  процедуры из разных ветвей `#Если` объединяются в одну, повтор имени в обычном коде по-прежнему ошибка.

### Финальная проверка платформой

Перед выгрузкой конфигурации обратно в 1С её можно проверить штатным способом:

```powershell
tools\build.ps1
dotnet tools\Data1c.PlatformCheck\bin\Debug\net10.0\data1c-platform-check.dll --dump C:\dump
```

Инструмент создаёт файловую информационную базу, загружает в неё конфигурацию из файлов
(`/LoadConfigFromFiles`) и запускает `/CheckConfig`, а журнал разбирает в замечания с местом, строкой
и фрагментом кода. На выгрузке 2,9 ГБ: создание базы 4 с, загрузка 844 с, проверка 430 с; замечания
выглядят так: `{ОбщийМодуль.X.Модуль(3,9)}: Ожидается выражение` и строка кода с пометкой `<<?>>`.
Место платформы переводится в путь файла выгрузки, поэтому замечание можно сразу открыть инструментом
`code`. Конфигурацию в базу нужно перечитывать после правки выгрузки — инструмент сравнивает базу
с самым свежим файлом. **Дешёвого пути нет, и это проверено отдельно:** `CheckConfig -ConfigDir <файлы>`
ошибок в коде не находит (484 с, повторяет замечания загруженной конфигурации), а частичная загрузка
`LoadConfigFromFiles -ListFile <файл>` отклоняется платформой за 12 с («редактирование объекта
метаданных запрещено»). Поэтому дорогая часть отделена: `--prepare` заранее создаёт базу и загружает
конфигурацию, `--check-only` проверяет подготовленную базу и **отказывается работать**, если она старше
выгрузки, а `--reuse` пропускает загрузку и честно помечает, что проверялась прежняя конфигурация.
Ключ `--json` печатает итог машиночитаемо, `--clean` удаляет базу после проверки.
Коды возврата: 0 — ошибок нет, 1 — есть ошибки, 2 — проверку не удалось выполнить. Пути к выгрузке
и базе не должны содержать пробелов: так устроена строка соединения 1С.

**Чего проверка не делает.** Ключ `--modules` (`/CheckModules`, секунды) **не находит ошибок в коде** —
это проверено внесением заведомой ошибки `Если Тогда` в модуль выгрузки: журнал сказал
«Синтаксических ошибок не обнаружено», хотя ошибка в базе была. Ловит её только `/CheckConfig`,
поэтому по умолчанию используется он.

## Направления развития

Подробный план работ с оценками и порядком — в [docs/BACKLOG.md](docs/BACKLOG.md).

- Структурный индекс справки платформы: не только темы, но и «тип → методы и свойства → сигнатуры»
  (разбор глав `V8SH_chapter` и блоков «Синтаксис»), чтобы автодополнение по точке давало список.
- Правило линтера «вызова нет ни в конфигурации, ни в платформе» — поиск опечаток по тексту модулей.
- Хранилище графа (SQLite) и запросы вида «кто использует реквизит X», «кто вызывает Y».
- Экспорт GraphML/GEXF для Gephi и Neo4j — когда встроенного просмотрщика перестанет хватать.
- Компактный формат выгрузки графа (CSV/Parquet) вместо JSON на гигабайт.
